## 🧪 测试

```bash
pytest
```

共 105 个测试，使用脚本化的 LLM 和假的搜索服务，离线几秒内跑完（Postgres 和 Neo4j 相关测试在本地没有这些服务时会跳过，CI 中会运行）。覆盖范围：

- **规划与修复**：并行分层执行、依赖传递、引用修复、证据不足后的重新规划、单个任务失败不影响其他任务。
- **忠实度**：论断抽取（包括中文文本和句末引用）、评审出错时按失败处理、只修复包含问题论断的那一节。
- **上下文工程**：大纲覆盖修复、按章节分配证据、压缩超预算的证据。
- **崩溃恢复**：硬崩溃后恢复且不重复搜索、预算耗尽暂停后继续。
- **worker 与租约**：两个 worker 分摊队列、接管无主运行，以及**另一个 worker 接管后，卡住的旧 worker 被 fencing 拦下**。
- **人工控制**：取消、暂停与继续、带修改 DAG 的计划审批。
- **工具层**：重放、用同一个键重试、等待人工核对、网页抓取、幂等推送。
- **API、SSE 与指标**。

CI 还会跑一次**部署演练**（[`evals/deploy_drill.sh`](../../evals/deploy_drill.sh)）：一个 API 和两个 worker 进程连到一个模拟的 OpenAI 兼容服务，其中一个 worker 在持有租约时被 `SIGKILL`；所有运行仍必须恰好完成一次。另一个任务会构建 Docker 镜像，并在容器内跑完一次运行。

## 💥 崩溃恢复基准

[`evals/crash_recovery.py`](../../evals/crash_recovery.py) 在一次脚本化运行的**每一个** LLM 调用、搜索调用、检查点写入和 webhook 推送处，用 `SIGKILL` 强制杀掉 worker 进程。这次运行包含一次章节修复、一次重新规划和一次向 webhook 推送报告，因此每个阶段都会被覆盖。随后由新进程恢复运行：每个新进程都要等被杀进程的租约过期，再用新的 fencing token 接管。每次实际执行的搜索和每次 webhook 发送都写入一个 fsync 过的副作用日志，因此跨进程的重复都能被统计到。模拟的接收端和 Stripe 风格的 API 一样支持 `Idempotency-Key`。

| 场景 | 崩溃的运行 | 恢复 | 报告与未崩溃时逐字节一致 | 出现重复搜索的运行 | 报告恰好送达一次 |
|---|--:|--:|--:|--:|--:|
| 在 LLM 调用前被杀 | 21 | 21/21 | 21/21 | 0 | 21/21 |
| 在搜索前被杀 | 8 | 8/8 | 8/8 | 0 | 8/8 |
| 在搜索**之后**、结果记录之前被杀 | 8 | 8/8 | 8/8 | 8 | 8/8 |
| 在写检查点前被杀 | 13 | 13/13 | 13/13 | 0 | 13/13 |
| 在 webhook POST 之前 / **之后**被杀 | 2 | 2/2 | 2/2 | 0 | 2/2（1 次重发，已去重） |
| **所有单次崩溃** | **52** | **52/52** | **52/52** | 8 | **52/52** |
| 同一次运行崩溃 2–3 次（随机） | 30 | 30/30 | 30/30 | 5 | 30/30（9 次重发，已去重） |

平均每次崩溃，恢复时会重新执行 **1.3 次 LLM 调用**（运行崩溃 2–3 次时为 2.0 次）。

**这些数字的含义：** 只读搜索是*至少一次*：如果在搜索完成、结果尚未记录时崩溃，这次搜索会被重复，但这无害。有副作用的推送在这种情况下也会再发一次，但带着同一个幂等键，所以接收端**在 82/82 次崩溃运行中都恰好处理了一次**。如果把固定的键换成随机键，同一个基准就会报告出重复推送。用量计数（token、调用次数）随运行一起写入检查点，因此被杀进程在最后一个检查点之后做的工作不计入。

```bash
python evals/crash_recovery.py    # 83 个场景，约 1 分钟；结果写入 evals/results/
```

## 🎯 真实模型评测

[`evals/faithfulness_eval.py`](../../evals/faithfulness_eval.py) 在 40 篇固定版本的 Wikipedia 文章上（[清单](../../evals/data/wikipedia_manifest.json)）跑 24 个研究问题。写作模型和运行中的评审都是 `gpt-4o-mini`。一个独立的 `gpt-4o` 评分模型对照证据全文，给每份最终报告里的每条带引用论断打标签。完整结果：[`evals/results/faithfulness_eval.md`](../../evals/results/faithfulness_eval.md)。

**论断评审能抓到注入的错误。** 错误只注入到评分模型标为*完全支持*的论断里，并且只保留评分模型确认确实出错的样本：

| 注入的错误 | 样本数 | 被运行中的评审发现（95% CI） |
|---|--:|--:|
| 把引用换成无关证据 | 132 | **99.2%**（95.8–99.9） |
| 最小的事实性改动（一个数字、实体或方向） | 54 | **100%** 被标出（93.4–100）；其中 74.1% 判为不支持/矛盾，其余判为*部分支持* |
| 对未改动的支持论断误报 | 129 | **0.0%**（0.0–2.9） |

**分章节写作限制了每次调用的上下文。** 与一次调用写完整份报告相比，报告阶段最大的那次调用在 **24/24** 个问题上都更小（中位数 **−41%**），代价是总调用次数更多。

**按章节分配证据节省 token 和上下文。** [`evals/routing_ablation.py`](../../evals/routing_ablation.py) 把按章节分配证据与一个自然的替代方案（每一节都看到全部证据）做比较（[结果](../../evals/results/routing_ablation.md)），共 24 个问题，给出配对 bootstrap 95% CI：

| | 按章节分配 vs. 每节全部证据 |
|---|--:|
| 每次运行的 LLM token | **−19.9%**（−13.3 至 −25.7） |
| 报告阶段 token | **−37.0%**（−28.7 至 −44.0） |
| 报告 prompt 中累计证据量 | **−61.6%**（−54.7 至 −66.9），23/24 个问题更小 |
| 最终报告引用了的研究发现 | 两者都是 **100%**（由核对环节强制保证） |
| 不支持或矛盾的论断 | 2.4% vs. 3.2%：没有增加（−0.8 个百分点，CI −4.1 至 +1.8） |
| 被判为*部分支持*而非完全支持的论断 | **+6.4 个百分点**（CI +3.2 至 +9.6） |

代价在于：看到的证据变少后，章节更常出现“说得比来源稍多”的论断（*部分支持*），但不支持或矛盾的论断没有变多。

**尚未证明：最终报告更好。** 在这个干净的语料上，基线本身的不支持论断就很少（3.3%）。评审进入循环后降到 2.2%，但配对 bootstrap 区间（−5.3 至 +4.0 个百分点）包含零。检测实验指出了原因：循环只修复*不支持*和*矛盾*的论断，而四分之一注入的事实性改动被判为*部分支持*。下一步是把*部分支持*的论断也纳入修复，并在另一组没用过的问题上评测。

```bash
python evals/fetch_wikipedia.py                          # 40 篇固定版本文章，约 2 MB（正文不入库：CC BY-SA）
python evals/faithfulness_eval.py runs grade detect report
```

## 🔎 检索

[`evals/retrieval_eval.py`](../../evals/retrieval_eval.py) 在同样的 40 篇固定版本 Wikipedia 文章（2,868 个文本块）上比较几种检索方法，使用人工标注的正确文章（[标注](../../evals/data/retrieval_labels.json)，[结果](../../evals/results/retrieval_eval.md)）。向量模型：`all-MiniLM-L6-v2`。

| 方法 | 48 个研究问题：Recall@5 | Recall@10 | 40 个改写查询：Hit@5 | MRR@10 |
|---|--:|--:|--:|--:|
| BM25 | 0.920 | 0.972 | 1.000 | 0.927 |
| 稠密向量（Faiss） | 0.920 | 0.938 | 1.000 | **0.983** |
| 混合（BM25 + 向量） | 0.917 | 0.944 | 1.000 | 0.963 |
| 知识图谱（Neo4j） | 0.906 | 0.955 | 0.600 | 0.523 |
| **混合（BM25 + 向量 + 图谱）** | **0.941** | **0.979** | 1.000 | 0.942 |

结论：
- **三路混合对跨主题问题覆盖最好。** 很多研究问题横跨两三篇文章，图谱通过共同的实体把它们连起来。
- **稠密向量对改写查询排序最好。** 对于刻意避开文章原词的查询，它更常把正确的文章排在第一。
- **单用图谱对改写查询效果差。** 查询里没有点名任何实体时，图谱无从下手，所以它只适合作为混合检索的一部分。

**局限：** 40 篇主题各不相同的文章，在文章级别上每种方法都接近上限，所以差距很小。更难的段落级基准（由 LLM 针对具体事实生成问题）已列入计划。
